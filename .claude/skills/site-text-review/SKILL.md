`$ARGUMENTS`의 글을 검토합니다. 이 검토는 글을 쓴 에이전트가 아닌 **별도의 서브에이전트**가 합니다. 글쓴이는 맥락을 알고 있어서 빈 곳을 스스로 채워 읽기 때문입니다.

## 입장

검토자는 Svelte를 써 본 개발자이고, 이 장을 처음부터 순서대로 읽는 독자입니다. 내부 구현은 모릅니다. 이 사이트의 목적은 **Svelte 사용자가 머릿속에 그림을 그리면서 내부 동작을 이해하게 하는 것**입니다. 문장 하나하나를 "지금 이 화면만 보고 무엇을 말하는지 그릴 수 있는가?"로 판단합니다.

## 먼저 읽을 것

1. `site/WRITING.md`: 문체와 흐름, 코드와 주석에 관한 지침입니다. 모든 항목이 검토 기준입니다.
2. 검토할 파일 전체입니다. 장 글이라면 조각(`<Beat>`) 순서대로 읽고, 각 조각에서 왼쪽 코드 무대에 무엇이 보이는지(`code`, `lines`, `at`/`note`, `whole`, `<Say>`, `<Point>`)도 함께 따라갑니다. 실험 컴포넌트(`site/src/lib/inside/**`)의 문구도 대상입니다.

## 학습자가 불러 준 문장

`<!-- 학습자 문장: … -->` 표시가 붙은 문장은 학습자가 직접 불러 준 문장이고, **어떤 검토 의견보다 우선합니다.** 이 문장의 낱말이나 어순을 바꾸자고 제안하지 않습니다. 이 문장 때문에 독자가 막히는 곳이 보이면, 문장은 그대로 둔 채로 풀 수 있는 방법만 제안합니다. 예를 들면 무대에 시각적 단서를 더하거나, 팝오버를 붙이거나, 앞뒤 문장을 보강하는 방법입니다. 보고에도 "학습자 문장이므로 그대로 두고"라고 밝힙니다.

## 확인할 것

조각마다 다음을 확인합니다.

- **지칭 대상**: "꺼낸 값", "이 값", "그 함수", "세 요소"처럼 무엇을 가리키는지 독자가 바로 알 수 있는가? 앞 조각을 다시 읽어야 알 수 있다면 문제입니다.
- **시각적 단서**: 문장이 코드의 어느 부분을 말할 때, 그 부분이 화면에 보이고 표시되어 있는가? 확인할 것은 다음과 같습니다.
  - 줄을 말하면 그 줄이 밝혀져 있거나 메모가 붙어 있어야 합니다.
  - 파일 전체("이 코드")를 말하면 `whole`로 그 파일이 표시되어 있어야 합니다.
  - 화면의 일부("줄 옆의 표시")를 말하면 `<Point>`로 감싸져 있어야 합니다.
  - 코드를 바꾸는 상황("두 번째 인자를 지우면")이면 바뀌는 부분이 무대에 표시되어 있어야 합니다.
  - 객관식 보기가 가리키는 대상이 화면에 보여야 합니다.
- **기억 부담**: 앞에서 한 번 나온 이름(`root()` 등)이 한참 뒤에 다시 나올 때, `<Recall>`로 다시 볼 수 있는가?
- **생성형 글 티**: "자리만 남겨서"처럼 비유로 동작을 뭉뚱그린 표현은 문제입니다. 연산이나 함수의 이름으로 직접 말해야 합니다(예: "`&` 연산으로 구합니다"). 그 밖에 WRITING.md가 금지하는 표현("엽니다", 가운뎃점, 화면 사용법 안내문, "~에서 일어나는 일" 제목 공식)도 확인합니다.
- **두 가지로 읽히는 문장**: 수식어가 꾸미는 말과 떨어져 있어서 무엇을 꾸미는지 두 가지로 읽히는가? 예: "에러 없이 런타임 상에서 파싱해 둔 노드가 일부 제외되므로"("에러 없이"가 무엇을 꾸미는지 모호함). 수식어를 꾸미는 말 바로 앞으로 옮기는 고친 문장을 제안합니다.
- **어색한 문장**: 기계적으로 고친 흔적이 있는가? 예를 들어 다른 장 제목을 바꾸면서 "~부터 차례로"처럼 원래 문장과 맞지 않는 말이 남아 있으면 문제입니다. 소리 내어 읽었을 때 걸리는 곳을 찾습니다.
- **맥락 없는 표현**: 독자가 모르는 구분, 내부 번호, 작성자의 공부 상황이 튀어나오지 않는가?
- **사실과 해석**: 소스나 실험으로 확인하지 않은 해석을 사실처럼 쓰지 않았는가?
- **근거 표기**: 무대에 이미 보이는 코드를 다시 "근거"로 적지 않았는가? 무대에 없는 파일의 근거는 마우스를 올리면 해당 줄이 보이는가(`<Ref>`)?

## 보고 형식

문제마다 다음 네 줄을 씁니다. 문제가 없는 조각은 적지 않습니다.

```
- 위치: 파일:줄 (조각 번호, 화면의 "N / 전체"로 셀 수 있으면 함께)
  원문: "…"
  문제: 독자 입장에서 무엇이 막히는지 한 문장
  제안: 고친 문장, 또는 필요한 시각적 단서(컴포넌트와 속성까지)
```

마지막에 "통과" 또는 "고칠 것 N개"로 끝냅니다. 직접 파일을 고치지 않습니다. 고치는 일은 글쓴이가 하고, 고친 뒤에 다시 이 검토를 실행합니다.
