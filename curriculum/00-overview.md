# 0단계: 로드맵과 학습 방법

## 전체 로드맵

| 단계 | 주제 | 핵심 질문 | 예상 기간 |
|---|---|---|---|
| [1단계](01-compiled-output.md) | 컴파일 결과 관찰 | 컴파일러는 `.svelte` 파일을 어떤 JS로 바꾸는가? | 2~4일 |
| [2단계](02-signals.md) | signal 시스템 | 값이 바뀌었다는 사실은 어떻게 전파되고, 무엇이 언제 다시 실행되는가? | 1~2주 |
| [3단계](03-dom.md) | DOM 계층 | signal 그래프 위에서 DOM은 어떻게 만들어지고 최소한으로 갱신되는가? | 1~2주 |
| [4단계](04-compiler.md) | 컴파일러 | 1단계에서 본 출력은 parse → analyze → transform을 거쳐 어떻게 만들어지는가? | 1~2주 |
| [5단계](05-archaeology.md) | 코드 고고학 | 5.0.0 이후에 무엇이 왜 바뀌었는가? | 1주 이상 |

예상 기간은 하루 1~2시간을 기준으로 잡은 대략적인 값입니다. 2단계가 가장 중요하며, 2단계를 충분히 이해하면 3단계와 4단계의 많은 부분이 자연스럽게 설명됩니다.

### 왜 이 순서인가

Svelte 3에서는 컴파일러가 대부분의 일을 했지만, Svelte 5에서는 반응성의 핵심이 런타임의 signal 시스템으로 이동했습니다. 컴파일러는 "템플릿을 복제하는 코드"와 "그 템플릿에 signal을 연결하는 effect"를 생성할 뿐입니다. 따라서 다음 순서로 공부해야 각 단계의 동기가 분명해집니다.

1. **출력을 먼저 봅니다.** 무엇이 만들어지는지 알아야 그것을 만드는 코드를 읽을 수 있습니다.
2. **런타임을 읽습니다.** 출력에 등장하는 `$.state`, `$.get`, `$.template_effect`, `$.if`가 실제로 무슨 일을 하는지 이해합니다.
3. **컴파일러를 읽습니다.** 이제 "왜 컴파일러가 이런 코드를 생성해야 하는가"를 알고 있으므로, 컴파일러 코드가 목적을 가진 코드로 읽힙니다.
4. **이력을 추적합니다.** 구조를 이해한 상태에서 PR을 읽어야, 각 변경이 무엇을 해결하려 했는지 판단할 수 있습니다.

## 질문 하나를 공부하는 방법

질문지의 각 질문에는 유형 태그가 붙어 있습니다.

| 태그 | 하는 일 |
|---|---|
| `[관찰]` | 도구를 실행하고 결과를 기록합니다. |
| `[예측]` | **실행하기 전에** 결과를 노트에 먼저 적고, 실행해서 맞았는지 확인합니다. 틀렸다면 왜 틀렸는지가 가장 중요한 학습 재료입니다. |
| `[추적]` | 코드에서 호출 경로를 따라가며 `file:line`을 기록합니다. |
| `[설명]` | 왜 이렇게 설계했는지, 다른 방식과 비교해서 무엇을 얻고 무엇을 포기했는지 설명합니다. |
| `[실험]` | lab을 수정하거나 새로 만들어서 가설을 검증합니다. |

권장하는 순서는 다음과 같습니다.

1. 각 단계 질문지의 "학습 경로" 표 순서대로 질문을 진행합니다.
2. 튜터가 질문지의 질문을 작은 유도 질문으로 쪼개서 하나씩 던집니다. 채팅으로 대강 답하면 됩니다.
3. 막히면 질문지의 `힌트 1`, `힌트 2`를 차례로 열거나, `/hint Q번호`로 더 구체적인 힌트를 요청합니다.
4. 답에 도달하면 튜터가 그 유도 질문과 다듬은 해설을 `notes/`에 기록합니다. 해설에는 근거(`file:line` 또는 실험 출력)가 반드시 붙습니다.
5. 공부하다가 질문지에 없는 의문이 생기면 튜터에게 바로 물어봅니다. 답이 나오면 튜터가 `log/tangents/`에 기록하고, 답을 아직 찾지 못한 질문은 `PROGRESS.md`의 "궁금증 백로그"에 둡니다. 스스로 떠올린 질문이 자기주도학습에서 가장 가치 있는 결과물입니다.

한 단계를 마치면 `/quiz 단계번호`로 체크포인트를 확인하고 다음 단계로 넘어갑니다.

## 런타임을 실험하는 방법

`tools/`와 `labs/`는 `svelte/packages/svelte/src`를 빌드 없이 직접 import합니다. 따라서 다음과 같은 실험을 할 수 있습니다.

- **로그 삽입**: `svelte/packages/svelte/src/internal/client/runtime.js` 같은 파일에 `console.log`를 넣고 lab을 실행합니다.
- **디버거**: `node --inspect-brk labs/02-signals/00-hello.mjs`로 실행한 뒤 Chrome의 `chrome://inspect`에서 붙거나, VS Code의 JavaScript Debug Terminal에서 lab을 실행하고 런타임 소스에 breakpoint를 겁니다.
- **일부러 망가뜨리기**: 특정 조건문을 지우거나 플래그를 바꾸고, `labs/`의 실험과 `npx -y pnpm@9.4.0 test signals`(svelte/ 디렉터리에서 실행)가 어떻게 실패하는지 관찰합니다. 무엇이 깨지는지를 보면 그 코드가 왜 필요한지 알 수 있습니다.

실험이 끝나면 `git -C svelte diff`로 수정 내역을 확인하고 `git -C svelte checkout -- <file>`로 되돌립니다. 의미 있는 실험이라면 되돌리기 전에 `git -C svelte diff > labs/NN-.../my-experiment.patch`로 저장해 두어도 좋습니다.

## 5.0.0과 최신 버전의 관계

1~4단계는 모두 `svelte@5.0.0` 기준입니다. 최신 코드(`main`)와 비교하고 싶다면 checkout하지 말고 다음 명령으로 읽습니다.

```bash
git -C svelte show main:packages/svelte/src/internal/client/runtime.js | less
git -C svelte diff svelte@5.0.0 main --stat -- packages/svelte/src/internal/client
```

1~4단계에서 "최신 버전에서는 어떻게 바뀌었을까?"라는 의문이 생기면 바로 확인하지 말고 `PROGRESS.md`의 백로그에 적어 두세요. 5단계에서 그 의문들을 직접 추적하게 됩니다.
